# 渐进超负荷规则链（调研条目 15）

来源：docs/open-source-research-2026-09-25.md 条目 15（设计借鉴 LiftLog 的规则链语义，未搬任何源码）。
引擎实现：`lib/engine/progression_chain.dart`（纯 Dart，全部可单元测试，见 `test/progression_chain_test.dart`）。

本文档与代码同口径：改引擎必须同步改这里；每条语义都配一个 Example 推演（学 LiftLog「规则文档 + Example 推演」配对写法）。

## 1. 概念

一条**规则链**（`ProgressionChain`）是有序的**规则**（`ChainRule`）列表，存在
`plan_exercises.rule` JSON 的 `chain` 键里（可省略——省略时由旧参数派生默认双阶梯，见 §3）。每条规则带四个属性：

| 属性 | 字段 | 取值 | 含义 |
|---|---|---|---|
| 轴 | `axis` | `reps`（次数）/ `load`（重量） | 这条规则推进哪个维度 |
| 步长 | `step` | 次数轴为整数；重量轴为正 kg | 每次推进的幅度 |
| 天花板 | `ceiling` | 数值或 null（不设限） | 当前轴位 >= 天花板时该规则**无空间** |
| 触顶后行为 | `advanceOnCap` | `true`=进位 / `false`=停住 | 无空间时跳到链中下一条，或整链停住 |
| 次数复位 | `resetRepsTo` | 整数或 null（不变） | 本规则执行后目标次数重置为该值（「加重归 8」的 8） |

另有**链状态**（`ChainState`）= `(重量档, 当前次数目标)`，以及两条执行门规：

- **达标门槛**：会话结束**计划组数内的非加练正式组全部达标**（每组 reps ≥ 当前次数目标，
  且末组 RIR 在**实际记录过**（`sets.rir_recorded=1`）时须 ≥ 目标-1）才推进链；
  未记录 RIR 时 `rir` 只是计划默认填充值，不参与判定，按次数达标即推进，reason 注明
  「余力未记录」。计划组没练够（X/Y）直接 hold，加练组无论次数
  高低都不参与 advance/hold/decrease。推进的是**链中第一条还有空间的规则**。
- **减重分支**：有组低于 `reps_min`（区间下限）→ 减重约 5%，链不推进
  （口径与旧引擎一致；负重量/辅助配重方向语义同旧引擎）。

## 2. 推进算法

```
达标？
├─ 否：有组 < reps_min → 减重 5%；否则 hold（重量与次数目标都不动）
└─ 是：沿链找第一条「还有空间」的规则
   ├─ 找到 reps 规则 → 目标次数 + step
   ├─ 找到 load 规则 → 重量 + step，目标次数 → resetRepsTo（缺省不变）
   ├─ 无空间且 advanceOnCap → 跳过，看下一条
   ├─ 无空间且 hold        → 整链停住（hold）
   └─ 全链无空间           → hold（「规则链尽头」）
```

**可达性检查**（学 LiftLog 的 unreachableFrom）：从链首看，第一条 `advanceOnCap=false`
的规则之后的全部规则永远轮不到（`ProgressionChain.unreachableRuleIndexes()`），
UI 将来可用它把死规则置灰。

## 3. 默认双阶梯（老数据派生）

老 JSON 没有 `chain` 键时，由旧参数派生标准双阶梯：

```
规则1：axis=reps, step=+1, ceiling=reps_max, 触顶进位
规则2：axis=load, step=increment_kg, 无天花板, 触顶停住, reset_reps_to=reps_min
```

### Example A：经典 8→12 加重归 8

规则：`reps_min=8, reps_max=12, increment_kg=2.5`（未配 chain，走派生链）。

| 场次 | 上次成绩 | 推导状态 (重量, 目标) | 判定 | 下次状态 |
|---|---|---|---|---|
| 1 | 60kg×8×8×8 | (60, 8) | 达标 → 规则1 有空间(8<12) | (60, **9**) |
| 2 | 60kg×9×3 | (60, 9) | 达标 → 规则1 | (60, **10**) |
| 3 | 60kg×10×3 | (60, 10) | 达标 → 规则1 | (60, **11**) |
| 4 | 60kg×11×3 | (60, 11) | 达标 → 规则1 | (60, **12**) |
| 5 | 60kg×12×3 | (60, 12) | 规则1 无空间(12≥12)→进位；规则2 有空间 | (**62.5kg, 8**) |
| 6 | 62.5kg×8×3 | (62.5, 8) | 达标 → 规则1 | (62.5, **9**) |

「8 爬到 12、然后加重归 8」不是任何一行硬编码——它是两条规则组合后
**自然涌现**的循环。对应单测：`progression_chain_test.dart` 组「双阶梯涌现」。

### Example B：老用户行为连续性

规则：`reps_min=5, reps_max=8, increment_kg=2.5`；用户一直顶格练 8×3。

- 旧引擎：`全部组 ≥ reps_max=8` → 加重 2.5。
- 新链：上次成绩推导目标 = min(reps)=8 → clamp 到 reps_max=8 → 第一次达标
  规则1 就无空间（8≥8）→ 进位 → 规则2 加重 2.5、复位到 5。

**重量结果与旧引擎一致**（62.5kg）；差异只在目标次数语义——见 §5。

### Example C：区间内爬升（语义升级点）

同一规则（5-8）；上次做了 7×3。

- 旧引擎：7 < 8 → hold（永远要求直接顶格 8）。
- 新链：目标推导为 7 → 达标 → 规则1 → 下次目标 8；再达标 → 进位加重归 5。

重量判定结果相同（hold），但次数目标从「一步登顶」变成逐场 +1 的平滑爬升。

### Example D：天花板停住

配了 `chain: [reps(1, ceiling 8), load(2.5, ceiling 62.5, hold)]` 的动作，
重量到 62.5kg 后再达标 → 规则2 无空间且 hold → 整链停住（文案「规则链尽头」），
不会跳过它去执行不存在的下一条。

## 4. 状态从哪来（无持久化状态机）

链状态**不落库**，每场训练结束时从「上次该动作的正式组」纯函数推导
（`chainStateFromHistory`）：重量 = 上次最后一组；目标次数 = 上次全部正式组的
最小 reps，clamp 到 `[reps_min, reps_max]`；无历史 = reps_min（重量由预设起始重量填）。

好处：不需要新表/新偏好键，换机/重装后状态天然可从历史重建；
代价：用户跨档乱练（>5% 波动）的场次不参与推导（口径与判定同源）。

## 5. 与旧引擎（evaluateProgression）的关系

- `evaluateProgression` 保留（`lib/engine/engine.dart`），现有测试继续有效；
- 生产路径（`_recommendFor` 起组建议、`verdicts` 总结建议）已切到规则链；
- 达标口径、减重口径、±5% 重量档位过滤与旧引擎逐项一致，唯一语义变化
  是 Example C 的次数目标爬升。

## 6. 相关：模板快照与统计纪律（调研条目 14）

渐进判定的数据地基是「训练记录不受模板日后修改影响」。口径（实现见
`lib/db/db.dart` 头注释，迁移见 `upgradeV5to6`）：

- **快照**：开始训练时把模板目标参数（目标组数 `target_sets`、次数区间
  `target_reps_min/max`）整套快照进 `session_exercises`（v6 起）；
  v6 前的老记录三列为 0，消费端回退 `rule` JSON 里的参数——平滑兼容。
- **PROGRAM_SESSION_KEY 的对应物**：本库一次训练由 `sessions.id` 外键串起
  全部动作行与组记录，无需额外键。
- **统计过滤纪律**：一切聚合查询显式 `sessions.status='done'`（排除进行中/
  放弃的会话）、容量统计只认 `kind='working'`（热身组不计）；模板表
  （plans/plan_exercises）天然不进统计。SQL 层锁定见
  `test/db_migration_test.dart`「统计过滤纪律」组。

## 7. 训练块、减载与停滞协议（P1-C，2026-10-18）

线性加重不能永远冲：规则链只回答「这次该不该加」，不回答「什么时候该退一步」。
P1-C 在链之外加一层周期与出口，纯函数在 `lib/engine/training_block.dart`
（块周/减载）与 `lib/engine/engine.dart` 的 `plateauProtocolOf`（停滞协议）。

### 7.1 训练块

- **块起点** = 当前计划第一次 `status='done'` 训练（`Db.firstDoneSessionOfPlan`）；
  计划还没有 done 记录时，本次训练即第 1 周。算出的锚点会存
  `block.anchor.<planId>`：训练日被删/重建后老会话会从 JOIN 消失，
  锚点缓存保证块周不静默重置；恢复备份带来更早的首场时锚点前移。
  锚点带**来源会话指纹**（id|date|startedAt，2026-10-18 起）：指向的那场
  done 会话被用户删掉后锚点失效，按「今天 = 第 1 周」重算，不再把已删
  会话的日期当块起点；计划指纹对不上（恢复备份的同号计划）同样失效。
- **块长** 默认 5 周，设置里可改（4/5/6/8 周等），**0 = 关闭**；
  第 N 周为减载周，减载周后的下一周回到第 1 周，开始下一块。
- 周次用 UTC 自然日差计算（`trainingBlockWeekOf`），跨月/跨年/夏令时不会算错一周。

### 7.2 减载处方

减载周在**开练时**把处方写进本场会话，训练中不随日期翻周变化：

- 建议重量 = 当前工作重量（链状态的重量 = 上次最后正式组）×0.9，
  向下取整到 0.5kg 网格（保证不超过 0.9×；2.5kg 档 → 2.0kg）；
  不是按链的「下次推荐」再打折（上次刚顶格时链会建议 +2.5，按推荐值
  打折只比原重量低 6%，不算减载）；自重 0kg 保持 0；
  负重量（辅助配重）按绝对值 ×1.1（配重更负 = 辅助更多 = 更省力）；
  横幅/总结对辅助器械写「辅助配重增加约 10%」，不写「90% 重量」以免
  被读成减轻辅助。
- 正式组数 = 计划组数 -1，最少 1 组（计划组数为 0/未知时保持 0，
  不凭空造组）；写进 `session_exercises.target_sets` 快照，页面流/进度/
  完成度判定同一口径。
- 起始页/休息页显示非弹窗横幅「本周减载」，动作页顶部条显示同款减载
  标记（只占宽度不新增高度，不遮挡动作名），说明下周回到原档。
- 减载会话在本机偏好里留下 `id|date|startedAt` 指纹
  （`block.deloadSessionIds`），下次处方与平台期回溯会跳过它——主动
  减载的 90% 重量不能把下一块的档位带低。恢复备份/换机后按指纹校验，
  同号但不同场的会话自动剔除，不会误排除真实训练。这批标记随全量
  备份导出/恢复一起迁移（2026-10-18 起，见 §9），训练块锚点同理。
- 本场块周/减载状态另存 `block.session.<id>`：训练中改块长、杀进程后
  恢复，仍按开练时的处方走完，不会把减载场翻成非减载。
- 「上次成绩」行仍显示**真实上一场**（包括减载场，例如 54kg）；只有
  下次处方与平台期回溯跳过减载，两者数据源分开（`lastWorkout` 与
  `_progressionLastWorkout`）。

### 7.3 停滞协议

数据源沿用 `plateauOf`（连续 ≥3 次同重量，或 ≥2 次且跨度 ≥12 天）：

| 平台期状态 | 协议 | 下一步 |
|---|---|---|
| 未顶格（次数 < 上限）且连续 ≥3 次 | `reduce` | 建议减载 10% 或换变式；自重动作只建议换变式 |
| 已顶格（次数 = 上限），无论 2 次还是 ≥3 次 | `add` | 保留加重建议（这是该加重，不是停滞）；自重动作改为加一组 |
| 2 次但跨 ≥12 天且**未顶格** | `none` | 维持原有「冲次数」提醒，不提前减载 |

总结页 `verdicts` 在以下三种情况用协议文案替换链文案：链的 hold 是
「次数没到目标」（`holdKind=target_miss`）、重量的次数轴推进（`advance`
但重量不变）、或链建议减重 5%（`decrease`，改用协议的 10% 减载）。
文案里带连续次数、天数、卡住的重量和原因；**链已成功加重**时保留链文案，
**少做/没记录/换档位**的 hold 也保留链原因（P0-B 的「本次只完成 X/Y 组」
不能被改写成「继续加重」）。训练页/休息页的平台期小字同样走协议。
2 次/12 天且未顶格的老口径不触发减载，避免把「间隔太久」误判成「练不动」。

## 8. 停练回归降档（P1-D，2026-10-18）

停练两周以上回来，上一场的重量会直接把人劝退。P1-D 在开练时按
「全库最近一场 `status='done'` 训练」判断停练天数，纯函数在
`lib/engine/layoff.dart`。

- **触发条件**：距上次 done 训练的自然日数 ≥14 天（第 14 天当天触发）。
  只认 done：active/quit 不算练过；临时训练也算一次 done 训练——
  只要还在练就不算停练。新用户没有 done 记录，不触发。
  「上次 done 训练」（`Db.lastDoneSessionDate`，2026-10-18 起两道纪律）：
  只认**有正式组（kind='working'）**的 done 会话——零正式组的空场不算
  "练过"；并**忽略未来日期**——设备时间被拨快留下的未来场不能永久
  压住停练判定。
- **处方**：建议重量 = 当前工作重量（链状态 = 上次最后正式组的实际
  重量）×0.85，向下取整到 0.5kg 网格；自重 0kg 保持 0；负重量
  （辅助配重）按绝对值 ×1.15（配重更负 = 辅助更多 = 更省力）；
  正式组数 -1（最少 1 组，0/未知保持 0），写进本场 `target_sets` 快照。
- **与减载周不叠加**：两者同时命中时取更低的重量系数（0.85 < 0.9），
  组数也只减 1 次；动作页只显示「停练 N 天」标记，减载横幅由停练
  横幅统一说明，避免「90%」与「85%」两套系数打架。
- **横幅**：起始页/休息页显示非弹窗横幅「停练 N 天，今天按 85% 找感觉」
  （同时是减载周时补一句「取更低的 85% 一档，不重复打折」）；动作页
  顶部条显示同款停练天数标记，不新增高度、不占三要素。
- **恢复**：回归场次在本机偏好里留下与减载相同的 `id|date|startedAt`
  指纹（`block.deloadSessionIds`），下次处方/平台期回溯跳过它——85% 的
  档位不能把下一场带低。下一次开练时距回归场 <14 天，自动回到停练前
  的档位；「上次成绩」行仍显示真实的回归场。
- **本场快照**：停练天数与是否回归随 `block.session.<id>` 一起落盘，
  杀进程/改日期恢复后仍按开练时的处方走完；升级前已在进行的会话
  没有该键，不追溯降档。

## 9. 本机标记随备份走（2026-10-18）

训练统计回溯的标记不全在 SQLite 里——`block.deloadSessionIds`
（减载周/停练回归场指纹）与 `block.anchor.<planId>`（训练块锚点 +
来源会话指纹）存在 SharedPreferences。全量导出/恢复（`Db.exportAllJson`
/ `Db.restoreAll`，自动快照与手动 JSON 存档共用）把它们带在 `prefs`
段里随数据迁移：

- **导出**：两键原样带上；未挂偏好（老测试路径）时该段为 null。
- **恢复**：数据库事务成功后写回偏好——锚点先清后写（不留指向已
  不存在计划的旧键），减载标记按备份时点带回或清掉。老备份没有
  `prefs` 段时**不动本机标记**：两类标记都自带指纹校验，对不上库内
  会话会被自动剔除，宁可少排除、不误排除真实训练。
- **恢复后接线**：控制器是 App 级单例，两个恢复入口（自动备份/
  JSON 存档）在恢复成功后调 `SessionController.reloadDeloadMarkers()`
  重灌内存排除表；锚点在下一次开练时从偏好现读，无需额外处理。
